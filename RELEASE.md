# Bouldr Stockroom

This release replaces the browser-only demo with a server-backed stockroom pilot. It is not a completed multi-site commercial SaaS product.

## Implemented

- D1-backed separate business workspaces; real workspaces start empty, practice workspaces have sample stock.
- Signed-in identity supplied by the Sites dispatcher. Server-side business membership checks on all private endpoints.
- Owner, manager, staff and viewer roles. Single-use, 24-hour invitation codes, shared manually. Site access must be granted separately through Sites.
- Products, units, case conversions, optional unit costs, barcodes and multiple stock locations.
- Receipts with pack quantities, loose units, optional supplier reference and private R2 image storage.
- Physical counts, recorded wastage, manual sales, versioned recipes, batch preparation and stock transfers.
- Draft purchase orders, external-order confirmation, partial receiving and cancellation of unreceived orders.
- Append-only changes and stock-movement records. Optimistic workspace revisions and request hashes protect against concurrent overwrites and repeated submissions.
- Stock exports including metadata and movement history. Photo bytes and self-service restore are not included.

## Limits and next connections

- Square requires account credentials; automatic webhook processing is not implemented. Manual sales must not later be imported again without reconciliation.
- No automatic image recognition. Photos are reference evidence and have a maximum of 8 MB each (JPEG, PNG, WebP).
- No supplier transmission, invoice reconciliation, accounting link, subscription billing or demand forecast.
- No automated backup/restore workflow, hardware integration or public customer onboarding.
- No lot-level depletion or traceability, expiry enforcement or assessed shelf-life calculation. Preparation dates are informational.
- Purchasing and order records are preserved within the workspace state. This release caps state size at 1.5 MB, products at 2,000, purchase orders at 5,000 and batches/history at 10,000. It needs normalised/paginated operational tables before high-volume chain use.
- Stock is synchronised on save, workspace load or manual refresh. It is not an offline-first or continuously streaming app.
- Counts should be performed with movements paused; stale revisions require explicit review.
- Cost values are user-entered purchase costs, excluding recoverable VAT. Missing costs remain visibly unknown. Reports are not accounting valuations or full profit reports.
- Unit changes are intentionally blocked after product creation. Different product sizes/flavours require separate products.
- Identity headers are trusted only because deployment is behind Sites' authenticated dispatcher; do not deploy this worker behind an untrusted public proxy without replacing the authentication layer.

## Verification

Run `npm run build` before `npm test`. Tests exercise the domain and API against an in-memory SQLite adapter implementing D1-style transactional batches. They cover persistence, rollback, tenant isolation, role checks, idempotency, same-version races, stock maths, recipe versions, partial receiving and the built Worker entrypoint.

Browser/mobile camera behaviour, hosted D1/R2 operations and real supplier/Square workflows need a controlled pilot. Passing local tests does not guarantee an error-free system.

## Recovery

Keep source and the saved version in Sites. Database migrations are generated by Drizzle and must become append-only after publication. Reverting a Worker does not automatically roll back database migrations or business records. Export records regularly before operational changes. Full restore needs a separately implemented and tested recovery path.


## 0.4 — Square preparation, Bouldr styling and notifications

- Orange/black Bouldr theme across navigation, dashboard, forms and cards.
- Dedicated Square section: exact variation/modifier rules, stock location mapping, explicit start date, catalogue reference import, paginated sales inbox, and review-before-apply.
- Read-only Square API adapter uses a server credential pinned to one business. Requires SQUARE_ACCESS_TOKEN, SQUARE_WORKSPACE_ID, and SQUARE_ENVIRONMENT (sandbox or production). It never writes to Square, takes payments or issues refunds. End-to-end merchant authorisation has not been exercised; multi-business OAuth and automatic webhook syncing remain future work.
- Seven practice cases for pints, packaged drinks, cocktails, unknown double modifiers, refunds, cancellations and vouchers. Practice data stays within practice workspaces.
- Deduplication is per Square order as well as per request. Imported orders that change after application are marked for review; no automatic reversal or second deduction. Imports retain stock-relevant fields and omit customer details.
- Low-stock email outbox uses Resend. Requires RESEND_API_KEY, EMAIL_FROM (verified sender) and NOTIFICATION_WORKSPACE_ID. No provider credentials or recipient were configured during development; no real emails were sent.
- Only the business owner can set the recipient, with explicit in-app confirmation. Practice workspaces never queue/send. Enabled real workspaces check after saved changes, at most once in 24 hours. There is no idle scheduled scan. A message lists quantities, targets and suggested pack top-ups; no supplier purchase is made.
- Emails have queued/failed/accepted/cancelled/expired statuses. Provider acceptance is not a delivery receipt. Stable provider idempotency keys reduce duplicate sends; retries stop before their 24-hour retention window expires. Failed messages can be retried by a manager. Full bounce/delivery webhooks, SMS and WhatsApp are not implemented.
- Initial 0000 migration is unchanged. Added 0001 square_orders and 0002 notifications migrations are additive.

## Authentication correction

Production requests were arriving with the dispatch-authenticated email but without the documented user-ID header, causing bootstrap 401 responses. The server now supports a namespaced, normalised authenticated-email identity when the ID is absent. Membership authorisation remains mandatory. The live membership table was empty before this correction; no existing member IDs were rewritten or merged. If the platform later changes identity header availability, reconcile identities explicitly rather than automatically joining accounts. This fallback must only run behind the Sites dispatcher, which owns the authenticated headers. Removed the sign-in link that was returning 404 in this environment.

## Faster delivery entry

Receipts begin with no assumed product. Saved barcodes can add a pack using typed/pasted codes or keyboard-style scanners. Unknown or ambiguous codes require manual selection; no camera recognition is implied. Each line has +1, 8-box and 9-box shortcuts, with the existing review-before-save step. Hardware behaviour has not been tested.
